OpenGL Renderer V2

The follow-up to my first renderer. V1 was about understanding the basics — textures, lighting, model loading. V2 pushes further into physically based rendering and uses the renderer as the visual half of a digital-twin experiment: a jointed robot arm driven by joint transforms, with the groundwork laid for mirroring a simulated machine in real time.

Development Journey

Why a V2

OpenGL Renderer V1 got the fundamentals right — the pipeline, a custom model loader, basic Phong-style lighting — but it was intentionally simple. V2 is a separate repo and a deliberate step up: real material response to light, an articulated object in the scene instead of static meshes, and the beginnings of using the renderer for something beyond pretty pictures — simulating and visualizing a physical system.

Physically Based Rendering

Materials now use a metallic/roughness PBR workflow instead of V1's simple Phong lighting, so surfaces respond to light in a far more physically plausible way. Image-based lighting groundwork is in — irradiance, pre-filtered environment maps, and a BRDF LUT pass — feeding into an HDR pipeline that loads real HDR skies (with a JPG skybox fallback) rather than flat ambient light.

Robotic Arm & Digital Twin

The centerpiece of V2 is a jointed robot arm, complete with its own forward-kinematics module and self-test tooling. The arm's pose is driven by joint transforms, and a TipWorld() query exposes the end-effector's world position — the hook that turns this from "a 3D model on screen" into "a renderer that can mirror the state of a simulated machine." That's the digital-twin angle: the virtual arm as the visual readout for a simulated or real system.

  • Jointed robot arm with forward kinematics (sim/RobotKinematics)
  • Dedicated RobotArm class separate from general scene geometry
  • Self-test tooling to validate the kinematics in isolation

Scene & Pipeline Upgrades

Model loading moved from V1's hand-rolled JSON loader to Assimp, trading a learning exercise for a far more capable, production-style pipeline. Shadow mapping, an HDR post-processing pipeline, and a primitives library (box, plane, sphere, cylinder) let scenes be built out of code rather than only imported assets — the current scene uses it for a ground plane, conveyors, crates and safety lines around the robot arm. A single ImGui controls panel ties the scene's toggles together.

Roadmap

This is active, unfinished work — some parts are rough by design while the architecture settles. What's next:

  • Finish the image-based lighting pipeline and add shadows to it
  • Inverse kinematics for the robot arm
  • Feed live or simulated data into the arm to complete the digital-twin loop
  • Basic physics and collision simulation
  • Cleaner scene and code structure
